A new barycentring engine computes the correction directly from astropy, ERFA and a
JPL ephemeris, with no PINT in the loop. It agrees with HEASOFT `barycorr` to within
the resolution the reference files can express (about 20 ns), it gives the same answer
on Apple Silicon as on x86, and it is some 30 times faster. It is not yet the default.

It is now the default. `--engine pint` keeps the old path available as an independent
cross-check, and for a `.par` file whose proper motion matters. Old ephemerides also work
again: `--ephem DE200` (or DE405, or a NANOGrav DE436) used to fail with an HTTP 404,
because astropy looks for every kernel in the one NAIF directory that no longer holds
them.

RXTE observations are now clock-corrected. HEASOFT `barycorr` ignores its own
`clockfile` parameter for RXTE and reads `tdc.dat`, 800 sets of quadratic coefficients in
free-format ASCII, so a copy of that file ships with the package and `read_tdc_file`
reads it -- translated from `xCC.c`, the reader `axBary` itself uses. The correction is
17.4 µs on the new test observation, and includes the PCA's extra 16 µs detector delay.
RXTE now agrees with `barycorr` to +25 ns on 404 events, with and without the clock
correction.

`clock_correction_fun` is the single entry point for clock corrections: give it a
mission, and it returns the correction function and the file it came from, or nothing for
a mission that needs none. `core.py` no longer names a mission anywhere.

When the source position is not given explicitly, the header keyword order stays
`RA_OBJ` → `RA_NOM` → `RA_PNT`, and now falls back to plain `RA`/`DEC` rather than
failing. That order is deliberately not HEASOFT's, which starts from the nominal
pointing: `RA_OBJ` is the position of the target itself, which is what arrival times
should be referred to. Because the two keywords routinely differ by a fraction of an
arcsecond -- 0.1 arcsec, or 172 µs of Roemer delay, on the NuSTAR test file -- a warning
now says which keyword was used, which one `barycorr` would have used, and how much time
the difference is worth. Comparisons against an official tool should pass `--ra`/`--dec`
explicitly, as every reference test here does; see "The coordinate keyword order is
deliberately not HEASOFT's" in the technical details.

XMM-Newton is now supported natively, and validated against SAS `barycen` to a constant
-42 ns on 401 EPIC-pn events. This is the one mission where the native engine is not a
convenience: HEASOFT `barycorr` refuses an XMM file outright ("Invalid
Observatory/Spacecraft position vector"), and `barycen` will not take an orbit file on the
command line at all -- it reaches the spacecraft position through SAS's observation access
layer, so using it means installing all of SAS and ingesting an ODF. We read the PPS
`P*OBX000ORBTSR*.FTZ` product instead, whose `GEI_X/Y/Z` columns are in kilometres.
Do not reach for the `GSE_*` triple beside them: it is the same vector rotated into the
Earth-Sun frame, it is exactly as long, and using it is a 160 ms error.

Chandra is now supported natively too, validated against CIAO `axbary` to +47 ns on 401
ACIS-S events. Like XMM, this is the only practical route: HEASOFT `barycorr` cannot do
Chandra at all -- `hdaxbary` carries orbit-file readers for RXTE, NICER, Swift and NuSTAR
only, and on a Chandra orbit file it fails with "no bracketing sample found" on a file
that brackets the time comfortably -- and `axbary` needs all of CIAO and can reach only
DE200 or DE405, which on this dataset is 79 µs from DE440. The orbit comes from
`primary/orbitf*_eph1.fits`, extension `ORBITEPHEM`, in metres.

Because `axbary` chooses its ephemeris from the reference frame, the Chandra test data
carries *two* references, DE405/ICRS and DE200/FK5. That pair is the first check of the
ephemeris/frame pairing against a real tool rather than against ourselves: DE200 is
referred to FK5 and DE405 onwards to ICRS, and pairing them the wrong way round is worth
11 µs.

Missions whose mission elapsed time counts *UTC* seconds rather than TT seconds are now
handled. `Mission.met_is_utc` turns on a leap-second term, computed from the file's own
`MJDREF` by `utils.leap_seconds_since_mjdref`, and applied before the barycentric
correction whether or not a clock file was given -- because it is a time-system
conversion rather than a clock model, and a flag should not be able to cause a
whole-second error. Only Swift needs it today.

Swift is supported natively, and validated against HEASOFT `barycorr` to **+37 ns** (max
59.6 ns, one unit in the last place of the reference's float64 times). The orbit comes from
the `PREFILTER` extension of the `auxil/sw<obsid>sao.fits` prefilter product, whose
`POSITION` and `VELOCITY` vectors are in kilometres, and the clock correction is the UTC
correction factor from the CALDB's `swclockcor*.fits`: quadratic coefficients per fit
interval in a `CLOCK_CORRECT` extension, worth −15.56 s on the test observation and
drifting 4616 µs/day. A time the clock file does not cover is refused rather than
extrapolated.

Swift also needs something no other mission here does. Its MET counts **UTC** seconds
rather than TT seconds, so it owes the leap seconds inserted since `MJDREF` — 4 s for a
2015 observation. That is a time-system conversion and not a clock correction, so it is
applied whether or not a clock file is given: `--clockfile none` cannot silently cost a
whole second. Missions opt in through the new `Mission.met_is_utc` field, and Swift is
currently the only one that does; Fermi shares Swift's `MJDREF` and may belong there too,
which is recorded in the known issues.

A clock file named by its bare filename is now looked up in `$TIMING_DIR` and then
`$LHEA_DATA` before being treated as a path, which is what HEASOFT `barycorr` does for
Swift. So `--clockfile swclockcor20041120v009.fits` resolves against an installed HEASOFT
the way it does for HEASOFT's own tasks, and the error when it resolves nowhere names both
variables. RXTE's `tdc.dat` already searched those two directories; they now share one
implementation.

`TIERABSO`, the absolute accuracy of the time in seconds, is now written into every
extension on any run that applies a clock correction, as `hdaxbary` does. Every mission's
clock builder returns a triple of `(correction, filename, accuracy)`, the accuracy being
a callable of the MET span so that a mission whose clock accuracy varies can say so.
Swift's 10 µs and RXTE's 5 µs match HEASOFT exactly; NuSTAR's comes out of the clock
file's own `CLOCK_ERR_CORR` column, as the worst value over the observation. With
`--clockfile none` nothing is written and any existing value is left alone.

The correction is no longer evaluated at every event on a large file. Above
`core.AUTO_GRID_EVENTS` (100 000) events it is sampled on a 5 s grid and interpolated,
which on a 3-million-event file takes the run from **23.0 s to 2.3 s and peak memory from
3.76 GB to 1.98 GB**, while leaving 99.03 % of the stored times bit-identical — the
largest difference being exactly one float64 step. Below the threshold the exact
per-event path is kept, so small files and every reference comparison in the test suite
stay unapproximated. The new `--dt` flag overrides the decision, and `--dt 0` forces the
exact path whatever the size.

`apply_barycenter_correction` now passes `met_range` to both engines, so a short
observation inside a multi-day orbit file no longer builds a grid across the whole file:
a 300 s snapshot in the 82800 s test orbit goes from 3.89 s to 0.12 s on the PINT path.
The range is derived from every extension's `TSTART`/`TSTOP` and then shifted by the clock
and leap-second terms, since that is where the correction is actually evaluated, and a
file whose times fall outside it is reported rather than quietly extrapolated.
